# Zeger Coffee — Technical Audit (July 2026)

Read-only snapshot of the current system. No runtime changes implied.

## 1. App Summary

Zeger Coffee is a multi-persona F&B operations app built on React 18 + Vite + Tailwind + shadcn/ui, backed by Supabase (Postgres, Auth, Storage, Edge Functions). It runs the daily operations of one coffee brand across a Central/Branch Hub, satellite branches, mobile Riders, an in-store POS, and a Customer ordering app. It is currently a **single-tenant** deployment; Zeger Coffee is intended to become **tenant #1** of a future SaaS F&B ERP.

Primary personas:
- **HO Admin / Finance** — back office reports, finance, master data.
- **Branch Manager / SB Branch Manager / BH Report** — branch-level ops, shift reports, cash deposit verification.
- **Kasir (BH / SB / numbered variants)** — POS front-of-house.
- **Rider (BH / SB / numbered variants)** — mobile sales, stock receive/return, cash deposit.
- **Customer** — order & pay via Xendit; assigned to nearest rider.

## 5. Edge Function Map

- `create-xendit-invoice` — creates invoice for `customer_orders`, returns URL.
- `xendit-webhook` — flips order to `paid`, writes `financial_transactions`, triggers dispatch.
- `send-order-request` — pushes new paid order to nearby riders.
- `rider-respond-order` — accept/decline handler.
- `get-nearby-riders` — geo query on `rider_locations`.
- `update-rider-location-live` — rider heartbeat.
- `process-void-transaction` — void flow with reversal.
- Auxiliary: notification/push helpers.

All Supabase secrets (Xendit, service role, Google Maps) are stored in Edge Function secrets, not in the repo.

## 6. Auth / Role Map

Auth: Supabase Auth (email/password); session hydrated by `useAuth`; guarded by `RoleBasedRoute` + `usePermissions`. Roles live in `user_role_permissions` (never on `profiles`) and are read via `has_role()` security-definer.

Role families in use today: `ho_admin`, `finance`, `branch_manager`, `sb_branch_manager`, `bh_report`, `bh_kasir`, `sb_kasir`, `bh_rider`, `sb_rider`, `rider`, `customer`, plus numbered aliases `1_*`, `2_Hub_*`, `3_SB_*`. Duplication between legacy and numbered names is a known cleanup target.

## 7. Rider Flow

1. Rider logs in → `MobileSellerEnhanced` shell loads.
2. If pending transfers exist → blocking confirmation screen (`MobileStockConfirmation*`).
3. After confirm → `inventory` incremented, sales tab unlocked.
4. Rider adds items (card click or `+`), chooses payment (Tunai / QRIS / Transfer). Payment proof is optional for non-cash.
5. On checkout → `transactions` + `transaction_items` insert, `inventory` decrement, `stock_movements` sale row.
6. End-of-shift → stock return, cash deposit (`Cash Sales − Op Expenses`), shift closed. Multiple shifts per day allowed.

## 8. Stock Transfer Flow

Branch Hub → Rider (single-cycle rule):
- Manager opens `StockTransfer`, picks rider + products.
- System **blocks** if rider has: active shift, pending unconfirmed transfer, remaining stock, or unverified report — with a clear pop-up message.
- On send → `stock_movements` `transfer_out` + branch `inventory` decrement.
- On rider confirm → `stock_movements` `transfer_in` + rider `inventory` increment.
- Riwayat Transfer Stok view (`Inventory.tsx`) groups by reference_id with Resume + Detail tables and TOTAL footers.

Production is decoupled: transfers no longer require a preceding production batch.

## 9. POS Flow

1. Kasir opens shift (`pos_shifts`, opening cash).
2. Cart built via `usePOSCart`; promos via `usePOSPromo`; bundles + custom items supported.
3. Payment via `POSMain.handlePay` → `pos_transactions` + `pos_transaction_items` insert → branch-level `inventory` decrement (`rider_id IS NULL`) → voucher marked used.
4. KDS ticket created in `pos_kds_tickets`; kitchen board is realtime.
5. Shift close → cash movements reconciled.

## 10. Customer App Flow

1. Customer browses menu, adds to cart (`CustomerCartNew`).
2. Checkout → address + payment method → `customer_orders` (`pending`).
3. `create-xendit-invoice` returns URL; customer pays externally.
4. `xendit-webhook` marks `paid`, writes `financial_transactions`, calls `send-order-request`.
5. Nearby rider accepts via `rider-respond-order`; order lifecycle tracked in `order_status_history`.
6. Loyalty accrual via `customer_points_history` + `customer_loyalty`.

## 11. Payment / Xendit Flow

- Invoice creation is server-side; amount is recomputed from DB to prevent client tampering.
- Webhook idempotency and signature verification are critical (P0 hardening).
- Financial recognition happens only when `paid` event is received.

## 12. Architecture Risks

- **Business logic in UI components** (POS pay, rider sale, stock transfer) — hard to test and reuse.
- **Large components** (`MobileSellerEnhanced`, `EnhancedShiftReport`, `POSMain`, `StockTransfer`, `RiderIncome`, `CashDepositHistory`) — high change risk.
- **Duplicated components / legacy pages** — divergence over time.
- **Role name duplication** (legacy vs numbered) — permission drift risk.
- **1,000-row Supabase cap** — must be handled by `.range()` loops everywhere aggregation is used.
- **Timezone** — Asia/Jakarta must be enforced; `toISOString()` is banned for DB dates.
- **Realtime subscriptions** — must be created inside `useEffect` with cleanup to avoid billing loops.
- **Secrets** — must never appear in client code; `.env` must remain ignored.

## 13. SaaS Readiness Notes

- No `tenant_id` on any table today; Zeger is implicitly tenant #1.
- Hardcoded tenant-specific values exist: verifier names, commission tiers, targets, categories, brand assets.
- Single Xendit account, single storage bucket layout.
- Roles are global, not tenant-scoped.
- Migration to multi-tenant will be additive and phased (see `docs/saas-blueprint.md`). No changes proposed now.
