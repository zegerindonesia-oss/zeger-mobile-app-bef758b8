# Project Architecture Rules

- Keep the cashier POS presentation isolated in reusable `pos-*` semantic classes and shared UI variants, so visual changes never alter transaction, access, inventory, or payment logic.- FlowF&B app SaaS website lives at / for signed-out visitors (HomeGate) and /landing; onboarding provisions tenant + owner membership + first branch + template menu via the provision_tenant RPC; flow_tenant_signups is kept as a sales lead log.

- Multi-tenant: `tenants` + `tenant_users` tables; tenant-scoped tables carry `tenant_id` defaulting to the Zeger tenant (00000000-0000-0000-0000-000000000001) so existing Zeger flows stay unchanged until tenant RLS is enforced per table.
- SaaS plans (ids free/sme/mid_market/enterprise) and their default modules live in src/lib/flow-plans.ts, mirrored server-side by public.plan_modules(); provision_tenant derives modules from plan so signups cannot self-grant modules.
- POS layout is touch-first: phones (<md) use full catalog + bottom cart drawer, tablets/desktop use split view; install support is manifest-only (no service worker) to keep previews safe.
- Native Android/iOS apps are Capacitor shells (capacitor.config.ts) loading the published domain, so APKs update without rebuilds; native folders are generated locally by the user via `npx cap add android`.
- POS TV queue screens pair without login via `/tv?branch=<id>` reading the minimal-field `get_queue_display` RPC; per-branch video/running text lives in `pos_display_settings`, so TVs never hold staff credentials.
- Per-branch POS config (order modes, hidden menu items, cash categories) lives in `pos_branch_settings`, edited only in Back Office (/settings/pos-branches); cashier POS reads it, so outlets cannot self-configure.
- Procurement (PO → receive → invoice/due date → payments) lives in purchase_orders/purchase_order_items/purchase_payments; receiving goes only through the receive_purchase_order RPC so stock-in and invoice totals stay atomic; access = is_material_manager() or a granted 'procurement' row in user_module_permissions (has_procurement_access).
- Material unit conversions live in material_units (factor to the material's base unit); recipes and stock always use the base unit.
- Invoicing is its own back-office module (/invoicing/*): sales invoices/orders live in sales_invoices(+items, doc_type invoice|order) with business_customers; purchase side reuses the procurement page; access reuses has_procurement_access so cashiers stay excluded.
- Accounting module (COA tree, journals via create_accounting_journal RPC enforcing debit=credit, ledger, trial balance) lives at /accounting/:tab; access reuses has_procurement_access.
- Rider stock orders to Central Kitchen live in rider_stock_requests(+items); Hub fulfils only via fulfill_rider_stock_request RPC, which creates 'sent' stock_movements (reference_type rider_request) priced at products.ck_price so the existing rider receive-confirmation flow is reused.
- Rider order leftovers use the shared shift-cycle picker on return created_at; rider-leftover calculates the latest returned cycle and same-shift waste, because later Hub verification must not combine separate shifts.
- Native apps: capacitor.config.ts builds three shells (POS, Rider, Customer) selected by APP_TARGET, each with its own appId and native folder under native/<target>, so the stores see three separate apps from one codebase.
- Bluetooth printing on native uses the local Capacitor plugin `plugins/bt-serial` (Classic SPP, paired devices, ids prefixed `spp:`) alongside BLE, because most label/thermal printers are Classic-only.
- POS cashier identity: staff sign into the POS terminal with a branch-scoped PIN (bcrypt in profiles.pos_pin_hash, verified via verify_cashier_pin RPC, set only by managers via set_cashier_pin); the active cashier is per-device and stamped as cashier_name on transactions/shifts, so one shared device login still attributes sales.
- POS reports (/pos/reports) and cashier cash/shift tools (/pos/cashier) are full pages inside POSPageShell so the sidebar stays visible.
- COGS calculator & menu engineering (/master/cogs) is read-only analytics: plate cost = recipe × raw_materials.cost_per_unit (auto-updated to latest purchase price by record_material_movement) + wastage %, classified with Kasavana & Smith in src/lib/menu-engineering.ts, so it never writes stock or prices.
- Loyalty rewards: reward_value JSON holds valid_hours (claim window, default 24) and product_id for free_product rewards; redeem_loyalty_reward stamps expiry/product on loyalty_redemptions, and POS + customer app both read member_benefits() so they always show the same vouchers.
- POS dine-in table QR uses /table?b=&t= (get_table_qr_info RPC, public minimal fields); context kept in sessionStorage and stamped as customer_orders.table_number, a trigger marks pos_tables occupied, so guests can order without installing the app.
- Back Office table configuration at /master/tables shares TableSetup and pos_tables/pos_table_sections with POS; HO branch selection is tenant-scoped and managers use their assigned branch, so QR and table settings have one source of truth.

- Table QR guests browse a minimal-field tenant-scoped menu RPC and submit an atomic server-priced dine-in bill to POS/KDS; guest phone never grants member access, and guest checkout uses pay-at-counter rather than claiming gateway payment.
- Customer phone sign-in uses Supabase SMS OTP and server-verified phone profile linking; existing email login remains as migration fallback, and SMS delivery requires the hosted phone provider to be enabled.
- Customer menu category priority is stored in app_settings and read through the RLS-protected get_customer_category_order RPC; chips and sections share customer-category-order helpers so new categories remain visible and QR guests receive the same ordering.
